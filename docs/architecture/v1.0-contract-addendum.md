## 3. 在线 CRUD 与 sync 的 tombstone 行为矩阵

| 操作 | 活跃资源 | 已软删除 tombstone |
|---|---|---|
| `GET by id` | 200 | **404** |
| `POST` 相同 id | 200 `created:false` | **404** |
| `PATCH` | 200；revision 不匹配则 409 | **404** |
| `DELETE` | 200；revision 不匹配则 409 | 200 `alreadyDeleted:true` |
| `sync UPSERT` | 正常 APPLIED/DUPLICATE/冲突 | **DUPLICATE + 当前 tombstone** |
| `sync DELETE` | APPLIED/DUPLICATE | **DUPLICATE** |

- 在线 CRUD 绝不返回 tombstone；tombstone 只在 `sync/push` 的 `record` 中返回，供客户端覆盖本地。
- Q-05/Q-06 修正原稿“POST/GET 已删除返回 200 tombstone”的表述：测试改为 404。
- Q-07 中 UPSERT tombstone 即使 `baseRevision` 匹配也不复活，始终 `DUPLICATE`。

## 4. 导出 token canonical 格式（供测试自签）

```text
payloadPart = base64url(JSON.stringify({
  v: 1,                       // 版本
  d: "<deviceHashHex>",       // 设备 HMAC 摘要 hex
  b: "<babyId uuid>",         // 宝宝 ID
  f: "YYYY-MM-DD",            // from
  t: "YYYY-MM-DD",            // to
  e: <unixSeconds>,           // 过期时间
  n: "<uuid v4>"              // nonce
}))
signature = base64url(HMAC-SHA256(APP_EXPORT_TOKEN_KEY, payloadPart))
token = payloadPart + "." + signature
```

- base64url 不带 padding；签名对 payloadPart 的 ASCII 字节计算。
- 字段名以已实现 `ExportTokenService` 为准（短名 `v/d/b/f/t/e/n`），测试自签必须使用同一格式。
- TTL 固定 300 秒，使用代码常量，不通过配置/环境变量暴露（测试用独立 key 自签过期 token）；下载路径 `/api/v1/exports/feeding-records/{token}.csv`。
- token 只含必要过滤条件；不在日志打印 token。

## 5. 同步锁与批次幂等的 Redis key（供测试预占）

设备作用域一律使用**设备 HMAC 摘要 hex**，不使用原始设备 UUID；默认前缀 `zz:bf:v1:`（与 `APP_REDIS_KEY_PREFIX` 一致）。

```text
同步批次锁：zz:bf:v1:lock:sync:{deviceHashHex}          // SET NX PX 15s
同步批次幂等：zz:bf:v1:sync:{deviceHashHex}:{batchId}   // 24h
```

- SYNC-16 预占锁时按上述完整 key 写入；测试与后端必须使用同一 `APP_REDIS_KEY_PREFIX`。
- 释放锁用 Lua compare-and-delete；Redis 故障时跳过锁，靠数据库幂等兜底。

- 前置：Q-19 已于 2026-10-26 裁决——出生日期等字段的 JSON 解析失败保持 `400 BAD_REQUEST`，不映射为 `VALIDATION_ERROR/fieldErrors`；本节不重复展开。
- 影响面：Q-20 backend-dev + test-engineer；Q-21 test-engineer；Q-22 frontend-dev + test-engineer（后端不改）；Q-23 test-engineer。
- 总原则：不改变接口 JSON 字段、端点或统一响应包形状；以下只锁定限流计数、Header 语义、客户端重试义务和 E2E 断言口径。

### Q-20 导出限流计数口径

**最终结论：导出 POST 限流只统计“成功签发 token”的请求（HTTP 200）；失败请求（400/413/500 等）不消耗导出口径配额。**

理由：
- 导出限流保护的是“成功签发 token 后产生的 CSV 生成/解密/下载资源”，400 参数错误不会创建可下载产物，也不应惩罚用户输错日期或宝宝 ID。
- 失败请求仍受通用 `api` 限流（120 次/分钟/设备）和 1 MB 请求体上限约束，滥用面已被覆盖。
- 成功签发仍严格限制 5 次/小时/设备；第 6 次成功请求才返回 429。

实现要求（backend-dev）：
- 进入导出 POST 时先原子预占一个配额（Redis Lua：如果当前成功计数 < 5 则 `INCR` 并放行，否则返回 429）。请求处理结束后，若响应非 2xx，则原子回滚该预占；若 2xx，则保留。这样避免并发请求同时通过检查导致超发 5 次。
- 配额已满时，即使请求体本来会 400，也直接返回 429（限流先于业务校验）；这是有意为之，避免已耗尽配额后继续消耗校验资源。

`X-RateLimit-*` 语义（导出 POST）：
- Redis 可用时，200/400/413/500 响应都返回导出作用域的 `X-RateLimit-Limit: 5` 与 `X-RateLimit-Remaining`：
  - 200：本次成功签发后的剩余值（5 → 4 → 3 → 2 → 1 → 0）。
  - 400/413/500：预占已回滚，剩余值与请求前一致，不因失败请求减少。
  - 429：`X-RateLimit-Remaining: 0`，并带 `Retry-After`（秒，最小 1）。
- Redis fail-open 时按 Q-18 不伪造限额头，记录告警。
- 通用 `api` 限流仍对所有请求计数；若通用限流先触发，按 Q-18 返回通用作用域的 429。导出接口正常响应头以导出作用域为准。

测试影响：
- EXP-09 不再需要“5 次 400 + 1 次 200 → 429”。改为：5 次非法请求均 400 且 remaining 不变；5 次成功请求 remaining 依次 4/3/2/1/0；第 6 次成功请求 429 + remaining 0。
- 可在同一设备完成，无需拆分设备；必要时用独立低阈值测试上下文或 Flush Redis DB。

### Q-21 CSV `Content-Type` 精确字符串

**最终结论：不要求空格精确匹配；按 MIME 语义判定等价。**

- 语义要求：媒体类型为 `text/csv`，charset 参数为 `UTF-8`；参数名/值大小写不敏感，分号后允许 0 个或多个空白。
- 测试使用正则：`(?i)^text/csv\s*;\s*charset\s*=\s*utf-8$`（如后端输出带引号，可放宽为可选引号）。
- Tomcat 输出 `text/csv;charset=UTF-8` 是合规的；后端无需为了加空格改实现，契约也不得以字符串精确相等作为断言。
- 影响面：仅 test-engineer 更新断言；无代码/接口形状变化。

### Q-22 sync 重放的客户端义务

**最终结论：选 A——保持服务端“整个请求体（含 `clientTime`）参与哈希”的语义，不改后端；由客户端保证同一 `batchId` 的重试请求体一致。**

理由：
- 现有契约已写“同 batchId + 相同请求体 → 回放；不同请求体 → 409”。把整个 body 纳入哈希能捕获客户端误改 payload 的情况，保留较强完整性。
- `clientTime` 虽是诊断字段，但冻结它的成本很低；排除它需要改服务端哈希并调整既有 409 用例，V1.0 集成阶段不值得为此放宽完整性。
- 客户端本来就应把一次同步尝试视为一个“批次计划”；批次计划应包含 `batchId`、`clientTime` 和 `changes`。

客户端义务（frontend-dev）：
- 同一 `batchId` 的网络重试必须复用**原始请求体**（至少 `clientTime` 和 `changes` 完全一致）；不得在重试时重新生成 `clientTime`。
- 建议把批次计划（batchId + clientTime + changes 序列化结果）持久化到 IndexedDB `meta`，或至少在同步重试循环内固定；若应用重启后无法复用原批次，生成**新的 batchId**（单条记录幂等仍由 id + baseRevision 保证）。
- 重试时不要重新排序/重建 changes；若必须重建，换新 batchId。

测试影响（test-engineer）：
- 同 batchId + 完全相同的请求体 → 200，`replayed:true`。
- 同 batchId + 仅 `clientTime` 改变 → **409 `CONFLICT`**（当前行为正确；任何期待回放的用例需改为 409）。
- 同 batchId + `changes` 改变 → 409。
- 新 batchId + 相同 changes → 正常处理；单条已处理记录由 item 幂等返回。
- 后端无改动；接口形状不变。

### Q-23 E2E “控制台无错误”口径

**最终结论：统一豁免浏览器自动产生的资源加载失败网络日志；只对真正的 JS 异常和业务 `console.error` 失败。不做逐 URL/逐状态码白名单。**

`expectNoPageErrors` 规则：
- 必须失败：`pageerror`（未捕获 JS 异常）。
- 必须失败：`console.error`，但匹配 `^Failed to load resource:` 的消息除外。
- 豁免：浏览器自动资源加载失败日志，包括任意 HTTP 状态（409/404/5xx）和 `net::ERR_*`；favicon 404 也由该规则覆盖。
- 不做 409 单独白名单；也不按 URL 白名单。
- CORS 类错误（如 `Access to fetch ... blocked by CORS policy`）不匹配上述前缀，应失败。
- 预期 HTTP 状态必须由 E2E 显式断言（`expect(response.status()).toBe(...)`）或 API 契约测试覆盖；`expectNoPageErrors` 只负责 JS 运行时健康，不负责证明接口成功。
- 影响面：仅 `tests/e2e/helpers/page.ts` 等测试辅助代码；无应用/后端改动。

## 7. Q-24（2026-10-26 追加）离线状态下的路由懒加载与导航失败

- 裁决日期：2026-10-26
- 影响面：frontend-dev、test-engineer；backend 无改动。
- 背景：5 个 Tab 均为路由懒加载。应用启动后仅 Home 入口 chunk 已下载；此时断网再点“记录”Tab，会在现场下载 `RecordsView-*.js/css`，失败后导航中止且无提示。

### 7.1 最终裁决

1. **“离线访问从未下载过 chunk 的路由”不属于 V1.0 的能力保证。** V1.0 的“应用已加载”指应用外壳 + **当前已进入过的路由**已加载；PWA/Service Worker 全量离线、未加载路由的离线访问均仍属 V1.1。核心 3 秒记录在 Home 已加载时仍可离线完成并同步，不受影响。
2. **“路由 chunk 加载失败必须给用户可见、可重试的提示”属于 V1.0 P1 要求。** 即使不做预取，静默无反应也不可接受；这是可用性缺陷，不是离线能力扩展。
3. **首页首屏稳定后的 idle 预取其余 Tab chunk 属于 V1.0 P2 最佳努力增强**（推荐实现，不作为离线验收门槛）。不引入 Service Worker；是否命中取决于网络与时机，不承诺离线可达。

### 7.2 修法选择

**选 (a) idle 预取作为 P2；不选 (b) modulepreload；不做 Service Worker。**

- (a) 实现约束：
  - 在应用挂载、首页今日数据请求结束、`load` 之后，使用 `requestIdleCallback`（Safari/iOS 14 无此 API 时用 `setTimeout(..., 2500)` 兜底，`timeout` 3s）依次 `import()` 其余 4 个 Tab 的路由组件；只加载模块，不挂载页面。
  - 网络门控：`navigator.onLine !== false`、`navigator.connection?.saveData !== true`、`effectiveType` 不是 `slow-2g/2g/3g`（Safari 无 `connection` API 时按 idle 时间兜底）。离线、省流、弱网直接跳过。
  - 预取失败静默记录 debug 日志，不弹错；用户真正导航时再走 P1 兜底。
  - 不预取 ECharts；统计/生长页的图表 chunk 仍保持页面内动态加载，避免把大包提前拉入。
  - 首屏预算不变：入口 JS 仍 ≤200KB gzip、CSS ≤50KB gzip；预取是首屏后的异步传输，不计入首屏预算，但需在 `frontend/README.md` 记录 4 个 Tab chunk 的 gzip 总量。不得阻塞首页首屏渲染或今日数据请求。
- 不选 (b) `modulepreload`：它会把 Tab chunk 拉进初始资源图，弱网下直接与首屏竞争，可能破坏 ≤1.5s / ≤200KB 预算；且加载失败仍需 P1 兜底，收益不如 idle 预取。
- 不做 Service Worker：V1.1 范围，需处理缓存版本、更新提示、微信 WebView 兼容，V1.0 不引入。

### 7.3 P1 导航失败兜底（契约级）

- 捕获点：`router.onError` 以及 `router.push/replace(...).catch`；识别动态 import 失败（`Failed to fetch dynamically imported module`、`Importing a module script failed`、`ChunkLoadError` 等）。非 chunk 类异常仍走全局错误处理。
- 交互：**模态对话框，不是一闪而过的 toast**；用户必须能重试或留在当前页。
- 固定文案：
  - 离线（`navigator.onLine === false`）：“当前网络不可用，页面尚未加载，请恢复网络后重试”
  - 其他/无法判断：“页面加载失败，请检查网络后重试”
  - 标题：“页面加载失败”
  - 按钮：“重试”（重新尝试原目标路由）、“取消”（留在当前页）
- 失败后当前路由不变；重试只允许手动触发，禁止自动无限重试。重复失败再次显示同一对话框。
- `data-testid`：对话框 `route-load-error`；重试按钮 `route-load-retry`。
- 文案、交互、testid 均以本 addendum 为准；frontend-dev 实现到统一常量/i18n 并同步 `frontend/README.md`，test-engineer 按此断言。后端无改动。

### 7.4 测试调整

- **UI-16 改为**：
  1. 在线启动应用，先进入“记录”页并等待其内容渲染（确保 Records chunk 已加载）；
  2. 返回首页（或留在记录页），再 `context.setOffline(true)`；

  4. 恢复网络，断言自动同步。
  - 禁止在离线状态下 reload 页面；冷启动离线不在 V1.0 范围。
- **新增 P1 用例**：

## 8. Q-25（2026-10-26 追加）请求体超限 413 与限流响应头

- 裁决日期：2026-10-26
- 影响面：backend-dev、test-engineer；frontend 无改动。
- 背景：`MaxBodySizeFilter` 在 `DispatcherServlet`/`RateLimitInterceptor` 之前对超过 1 MB 的请求直接返回 413，因此该响应没有 `X-RateLimit-*`，也不消耗导出配额。Q-20 原文的「400/413/500 仍返回导出限流头」未区分此类早于限流器的 413。

### 8.1 最终裁决

1. **不要求**该早于限流器的 413 带 `X-RateLimit-*`。它没有进入限流器，限流器未做任何判定，不应伪造限流状态。
2. **不要求**为补头而只读计数。该路径不预占、不消耗导出配额；也不为了返回 Header 去解析设备并读取 Redis。
3. **通用 `api` 限流在该 413 路径同样不生效，属于可接受行为。** 请求在限流器和任何业务处理之前已被拒绝，不产生业务/CSV 资源；1 MB 上限本身限制了单次成本，外层基础设施限流负责兜底。无需在 `MaxBodySizeFilter` 内重复实现应用限流。

### 8.2 精确语义（按错误码区分两类 413）

| 场景 | code | 是否经过限流器 | `X-RateLimit-*` | 配额 |
|---|---|---|---|---|
| 请求体 >1 MB，被 `MaxBodySizeFilter` 提前拒绝 | `PAYLOAD_TOO_LARGE` | 否 | **不返回** | 导出配额与通用 `api` 配额均不消耗 |
| 导出参数通过后，日期跨度 >366 天或行数 >10,000 | `EXPORT_TOO_LARGE` | 是 | 按 Q-20 返回导出作用域头 | 预占后因非 2xx 回滚，`Remaining` 与请求前一致；通用 `api` 仍计数 |

- Q-20 中「400/413/500 仍返回导出限流头」的 **413 仅指 `EXPORT_TOO_LARGE`**；`PAYLOAD_TOO_LARGE` 由本节覆盖。
- 其他在 `RateLimitInterceptor` 之前产生的拒绝，同样不返回限流头、不消耗配额；一旦请求到达限流器，按 Q-18/Q-20 执行。
- Redis fail-open 时仍按 Q-18 不伪造限流头。
- 该裁决不改变统一响应包、错误码或接口形状；`PAYLOAD_TOO_LARGE` 与 `EXPORT_TOO_LARGE` 继续用现有 code 区分。

### 8.3 测试调整

- 对导出端点发送 >1 MB 请求体：断言 HTTP 413、`code=PAYLOAD_TOO_LARGE`、**无** `X-RateLimit-*`；随后连续 5 次合法导出仍成功，`Remaining` 依次为 4/3/2/1/0，证明配额未被该 413 消耗。
- 对普通业务端点发送 >1 MB 请求体：断言 413、无 `X-RateLimit-*`；在低阈值测试上下文中，后续正常请求的 `api` 配额不因该请求减少。
- 发送跨度 367 天的导出请求：断言 413、`code=EXPORT_TOO_LARGE`、带导出作用域 `X-RateLimit-*` 且 `Remaining` 不减少。
- 不得用「所有 413 都无 Header」作为断言；必须按 `code` 区分两类 413。

### 8.4 通知要点（可直接转发）

- backend-dev：`MaxBodySizeFilter` 的早拒绝 413 保持现状，不补限流头、不读 Redis；确认其 code 为 `PAYLOAD_TOO_LARGE`，与导出业务的 `EXPORT_TOO_LARGE` 可区分。
- test-engineer：新增上述两类 413 用例；Q-20 的导出头断言只适用于 `EXPORT_TOO_LARGE`。

## 9. Q-26（2026-10-26 追加）路径规范化与端点作用域限流

- 裁决日期：2026-10-26
- 影响面：backend-dev、test-engineer；frontend 无改动。
- 背景：CR-01 实测 `/api/v1/sync/push;a=1` 可命中业务 Handler，但基于原始 `requestURI` 的作用域匹配未命中，从而绕过 `sync` 专用限额；`export`/`init` 存在同类风险。

### 9.1 最终裁决

**需要写入契约：所有基于路径的限流作用域判定、设备头豁免、健康检查/导出下载豁免，必须使用规范化后的路由路径；禁止直接对原始 `requestURI` 做字符串前缀/后缀匹配。**

矩阵参数（`;a=1`）、查询串、百分号编码等不得改变端点作用域。该要求不改变接口形状，属于安全边界。

### 9.2 精确规则

- 作用域按**匹配到的路由**判定，而不是原始 URI。实现优先使用 Spring 的 `HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE`；若必须在 HandlerMapping 之前判定，使用 `UrlPathHelper`（移除 semicolon content）得到的 lookup path。
- 路径规范化至少满足：
  - 去掉每个路径段上的 matrix parameters（`;...`），例如 `/api/v1/sync/push;a=1` 与 `/api/v1/sync/push` 同属 `sync` 作用域。
  - 忽略查询串；`?a=1` 不改变作用域。
  - 不做大小写折叠；`/API/V1/...` 不得被当作已注册端点。
  - 不得因尾部斜杠、重复斜杠或编码差异把受保护端点判成豁免端点。
- 下列判定全部使用同一规范化路径：
  - `init` / `export` / `sync` / 通用 `api` 限流；
  - `GET /api/v1/health` 的设备头豁免；
  - `GET /api/v1/exports/feeding-records/{token}.csv` 的设备头豁免。
- 矩阵参数本身不要求拒绝；它可以继续被业务忽略。但**不能**因此绕过专用限额、设备头校验或豁免判定。
- 若某请求无法可靠规范化，按已注册端点中最严格的作用域处理，不得回退为“无限流/免设备头”。

### 9.3 测试调整

- `sync`：在低阈值上下文内用满额度后，第 N+1 次请求 `POST /api/v1/sync/push;a=1` 必须返回 429 `RATE_LIMITED`，带 `sync` 作用域 `X-RateLimit-*` 与 `Retry-After`；与不带 matrix 参数共用同一计数器。
- `export`：5 次成功签发后，第 6 次 `POST /api/v1/exports/feeding-records;x=1` 必须 429（导出作用域），不得因路径变体成功签发。
- `init`：达到 IP 小时限额后，`POST /api/v1/devices/init;x=1` 必须 429（`init` 作用域）。
- 至少覆盖一个查询串变体（如 `?x=1`）与一个带 matrix 参数的变体；断言它们与规范路径共享计数。
- 设备头豁免不得被路径变体扩大：受保护端点加 matrix 参数后仍必须要求 `X-Device-Id`。

### 9.4 通知要点（可直接转发）

- backend-dev：限流/豁免的作用域匹配改为使用规范化路由（`BEST_MATCHING_PATTERN_ATTRIBUTE` 或移除 semicolon 的 lookup path），不得用 `getRequestURI()` 直接匹配；N-7 修复需覆盖 init/export/sync 三处。
- test-engineer：在 Q-12 低阈值上下文补充 `;a=1`、`?x=1` 变体用例，断言与规范路径共享计数；同时验证设备头豁免不被路径变体绕过。

## 10. Q-27（2026-10-26 追加）导出跨度超限的状态码与 `data` 形状

- 裁决日期：2026-10-26
- 影响面：backend-dev、test-engineer；frontend 无强制改动。
- 背景：主契约 §4.9 与 Q-25 §8.2 均写「跨度 >366 天或行数 >10,000 → 413 `EXPORT_TOO_LARGE`」，但 `ExportValidator.validateRange` 对跨度超限抛 400 `VALIDATION_ERROR`，`EXP-09` 按实现断言 400，`EXP-14` 因此被跳过。

### 10.1 最终裁决

1. **跨度 >366 天返回 413 `EXPORT_TOO_LARGE`，不是 400 `VALIDATION_ERROR`。**
   `from`/`to` 本身是合法日期，跨度是导出资源上限，不是字段格式错误；主契约的错误码表也已把 `EXPORT_TOO_LARGE` 定义为「导出范围/行数超限」。按契约实现，不按旧实现反向改契约。
2. **`from > to` 仍为 400 `VALIDATION_ERROR`**；日期缺失/格式错误仍按现有校验返回 400。Q-27 只改变跨度超限。
3. **跨度按含首尾天数计算**：`spanDays = ChronoUnit.DAYS.between(from,to) + 1`；允许 `spanDays <= 366`，`spanDays = 367` 即超限。
4. **该 413 发生在 Q-20 预占之后**：失败必须回滚预占，`X-RateLimit-*` 仍返回导出作用域头，`Remaining` 与请求前一致；若配额已耗尽，仍按 Q-20 先返回 429，不进入跨度校验。

### 10.2 `data` 精确形状（两个互斥变体）

跨度超限：

```json
{
  "maxDays": 366,
  "from": "2025-10-19",
  "to": "2026-10-20",
  "spanDays": 367
}
```

- `from`/`to` 为解析后的 canonical `YYYY-MM-DD`，不是请求原始字符串。
- `spanDays` 为含首尾整数；`maxDays` 固定 366。
- **不包含** `rowCount`/`maxRows`：跨度校验先于行数统计，未执行行数查询。

行数超限（保持现有形状）：

```json
{
  "rowCount": 10001,
  "maxRows": 10000
}
```

- **不包含** `maxDays`/`from`/`to`/`spanDays`。
- 两个变体不共用同一 `data` 形状，也不新增 `limitType` 等判别字段；客户端按 `maxDays` 或 `maxRows` 是否存在区分。
- 两类不会同时出现：先校验跨度，跨度合法后才统计行数；跨度超限时不做行数查询。
- `message` 只要求人类可读，客户端不得依赖精确文案；以 `code` 和 `data` 为准。
